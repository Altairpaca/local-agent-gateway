# v0.2 acceptance contract

v0.2 closes the cloud-testable control-flow gap between authorization and a future real local runtime adapter.

## Dispatch order

For a new request, the dispatcher must enforce this order:

1. completed/in-flight request-ID replay/conflict check;
2. grant authorization;
3. logical project lookup;
4. local agent lookup;
5. adapter capability declaration check;
6. adapter execution;
7. receipt creation and ledger recording.

No adapter may be invoked before steps 1–5 pass.

## Registry boundary

Remote requests carry `projectId` and `agentId` only. A project root is supplied by the machine-local `ProjectRegistry`. Runtime adapters receive the resolved root but cannot cause the remote protocol to acquire arbitrary-path authority.

The static registries are deterministic reference implementations. Production storage or dynamic discovery can replace them without changing the authorization contract.

## Idempotency boundary

Request IDs are authority-sensitive for completed and concurrent requests. Replay identity binds the request to the full normalized grant authority: grant ID, subject, session, validity window, capabilities, projects and agents. Set-like grant arrays are sorted before fingerprinting so semantically equivalent ordering does not create a false conflict.

- exact same grant authority + request payload after a completed dispatch returns the original receipt and does not re-execute;
- an identical request arriving while the first execution is still in flight joins the same execution and returns the same receipt as `replayed`;
- the same request ID with changed grant authority or request payload is denied as `request-id-conflict`, including while the original request is still in flight.

This protects against sequential and concurrent double execution without allowing a request ID to be rebound to broader or merely different authority.

The in-memory ledger and in-flight map are reference implementations of these semantics. They are not presented as crash-safe, distributed or multi-process coordination. A durable deployment must preserve equivalent uniqueness/atomicity semantics in its persistence layer.

## Adapter failure semantics

Once authorization and registry checks pass, an adapter invocation is an executed dispatch even if the adapter throws. A thrown adapter error is converted into a `lag.receipt/v1` receipt with `outcome: failure` and a canonical SHA-256 digest over the bounded error identity. The raw stack is not inserted into the receipt.

The completed failure is recorded in the request ledger, so an exact retry replays the same failure receipt rather than executing the side effect again. Runtime-specific adapters may provide richer sanitized evidence through their normal `AdapterExecutionResult` failure path.

## Receipt semantics

Denied dispatches also produce `lag.receipt/v1` receipts with a canonical SHA-256 evidence digest over the denial reason and request. The receipt proves deterministic content integrity only; it is not a cryptographic identity signature.

## Cloud-only acceptance

The following are fully exercised with fake adapters in GitHub Actions:

- deny-before-execute ordering;
- unregistered project and agent denial;
- adapter capability mismatch denial;
- sequential exact replay without duplicate execution;
- concurrent exact replay with at-most-once adapter invocation inside one dispatcher instance;
- concurrent/sequential request-ID conflict denial;
- grant-authority changes under the same request ID are conflicts;
- set ordering does not change replay identity;
- adapter exceptions become replayable failure receipts;
- local registry root delivery to the adapter;
- receipt integrity for executed, failed and denied paths.

Real Codex/Hermes/OmO protocols, tunnel authentication and human approval UX remain outside v0.2 cloud-only acceptance.
